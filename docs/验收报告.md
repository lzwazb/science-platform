## 五、知识共建（项目核心）

### ☑ 7. 用户能提交知识补充/纠错建议，必须包含必要字段并保存来源信息

**实测（T06）**：缺字段时
`400 reason 提交理由不能为空；referenceSource 参考来源不能为空；suggestedContent 建议内容不能为空`，
且数据库无新增记录（测试比对前后条数）。

四个必填字段：`articleId`、`contributionType`、`suggestedContent`、`reason`、`referenceSource`。

### ☑ 8. 评审员能通过/驳回贡献并填写意见；提交者可查看处理结果

**实测（T07）**：
- 驳回不填意见 → `400 驳回时必须填写审核意见`
- 驳回填意见 → `REJECTED`，提交者在「我的贡献」看到状态与意见
- 评审员访问 → `200`；创作者访问审核接口 → `403`

### ☑ 9. 通过知识贡献后，正式文章内容更新，历史版本保存，相关通知生成

**实测（T08，端到端）**：对文章 8 提交纠错并通过后

| 项 | 变化 |
| --- | --- |
| 文章 `version_no` | 1 → 2 |
| 文章正文 | 523 字 → 596 字 |
| `article_version` | 新增 `version_no=1` 快照，内容为变更前的 523 字 |
| `source_contribution_id` | 指向该贡献，可追溯 |
| `sys_notification` | 新增 1 条 `REVIEW_RESULT` 给提交者 |
| `sys_operation_log` | 新增 `CONTRIBUTION_APPROVE` |

### ☑ 10. 审核被重复提交或重复处理时，系统不会产生错误的重复更新

两层防护：

1. 状态预检查：非 `PENDING` 直接 `400 该建议当前状态为已通过，不能重复处理`
2. 条件更新：`UPDATE ... WHERE id = ? AND status = 'PENDING'`，`affected == 0` 抛异常触发整体回滚

**实测**：重复通过 → `400`，且不产生第二条历史版本。

**T09 事务回滚**：用 `@MockitoBean` 让写快照抛异常后，
文章版本号与正文未变、贡献仍为 `PENDING`、`reviewerId`/`reviewedAt`/`finalContent` 全为 `null`、
通知与日志均无新增。

## 二、建议完成项

### ☑ 3. 知识贡献并发更新校验

**问题**：同一文章存在多条待审核贡献时，两位评审员同时通过，两个事务都读到同一个
`version_no`，会写入相同版本号的历史快照。

**方案（两层）**：

1. `ScienceArticleMapper.selectByIdForUpdate`——`SELECT ... FOR UPDATE` 行锁，
   第二个事务等待第一个提交后再读，拿到的是最新版本号
2. `uk_article_version(article_id, version_no)` 唯一索引兜底，
   并把 `DuplicateKeyException` 转成业务提示「文章版本已变化，请刷新审核详情后重试」

**未改动**：历史版本记录结构、审核事务边界、既有审核流程。

**实测（新增 `ContributionConcurrencyTest`，2 个用例）**：

| 场景 | 结果 |
| --- | --- |
| 两条不同贡献并发通过 | 无重复版本号；成功数 = 快照数；文章版本号 = 初始值 + 成功数 |
| 同一条贡献被并发重复处理 | 只产生 1 条快照，文章只升 1 个版本 |

> 该测试类**刻意不加 `@Transactional`**：Spring 事务上下文基于 ThreadLocal，
> 子线程里调用 Service 会开启独立事务；如果测试方法自带事务，子线程看不到未提交数据，
> 行锁行为也和真实并发不一致。因此改为手动准备与清理数据。

# 权限调整：普通用户可参与创作与活动投稿

> 依据使用反馈调整：「参与活动」不应只对 `CREATOR` 开放

## 调整内容

| 路径 | 调整前 | 调整后 |
| --- | --- | --- |
| `/api/v1/creator/**` | `CREATOR` / `ADMIN` / `SUPER_ADMIN` | **已登录用户** |
| `POST /events/{id}/submissions` | 同上 | **已登录用户** |

同时在 `CreatorWorkController`、`EventSubmissionController` 上把
`@PreAuthorize("hasAnyRole('CREATOR','ADMIN','SUPER_ADMIN')")` 改为 `isAuthenticated()`。

## 为什么这样改

1. 平台定位是「科普**共创**」，创作与参与活动属于普通用户的正当权益
2. 安全边界本来就不在角色上——作品创建后是 `DRAFT`，必须审核通过才变 `PUBLISHED`，
   之后才能公开、才能投稿。真正把关的是审核流程
3. 原来存在连锁阻断：普通用户不能创作 → 没有作品 → 活动投稿即使放开也走不通

`CREATOR` 角色保留，降级为「认证创作者」的展示标识，不再承担功能权限。

## 越权防护核对（未松动）

| 场景 | 结果 |
| --- | --- |
| 投稿他人作品 | `403 只能提交自己的作品` |
| 未发布作品投稿 | `400 只有已发布的作品可以投稿` |
| 普通用户访问审核台 `/review/**` | `403` |
| 普通用户访问后台 `/admin/**` | `403` |
| 未登录访问创作者中心 | `401` |
| 未登录访问投稿接口 | `401` |

## 完整链路实测（user01，仅 USER 角色）

```
角色确认                        USER
进入创作者中心                  200
创建作品                        200  DRAFT
提交审核                        200  PENDING
未通过就投稿                    400  只有已发布的作品可以投稿  ← 业务规则而非权限
评审员审核通过                  200  PUBLISHED
再次投稿活动                    200  投稿 #22
我的投稿列表                    200  1 条 SUBMITTED
投稿他人作品                    403  只能提交自己的作品
访问审核台                      403
访问后台                        403
```

第 5 步是本次调整的关键证据：**拦住它的是「作品未发布」，不是「没有权限」**。
