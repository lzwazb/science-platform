# 需求分析

> 论文材料 · 对应开发档案第 2、3、4 章。
> 本文档在阶段 2 完成，后续阶段如需求有调整应同步修订，避免论文表述与代码不一致。

## 1. 项目背景与定位

科普内容的生产长期存在两个断裂：一是专业内容与公众理解之间的断裂，二是单向传播与读者反馈之间的断裂。前者表现为文章写得准确但不好读，后者表现为读者发现错误却只能写在评论区，无法真正影响正式内容。

本项目针对第二个断裂设计：把「读者纠错」从评论区提升为一条带审核的正式流程——读者提交补充、纠错或改写建议，必须填写理由与参考来源；评审员决定是否采纳；采纳后正式文章更新，同时保留历史版本，形成可追溯的内容演进链。创意作品则作为知识的二次表达，与文章建立显式关联，让「读」与「创作」形成闭环。

平台定位为参与式科普内容平台，不是后台 CRUD 管理系统，也不是通用内容社区。这一判断决定了下面所有需求的取舍标准：凡是不能强化「知识共建」与「知识—作品关联」的功能，优先级一律下调。

## 2. 可行性分析

| 维度 | 分析 |
| --- | --- |
| 技术可行性 | 采用 Spring Boot + Vue 前后端分离单体架构，全部为成熟稳定组件；核心难点（审核事务、版本快照、权限校验）在关系型数据库与事务能力范围内，无需引入消息队列、缓存或搜索引擎 |
| 数据可行性 | 演示阶段使用人工核对过的公开科普内容，来源标注真实机构官网；不依赖第三方数据接口，避免外部服务不可用影响演示 |
| 时间可行性 | 分为 11 个阶段（阶段 0–10），每阶段独立可验证；P0 范围限定为七个模块的主流程，P1/P2 功能按剩余时间取舍 |
| 操作可行性 | 界面为中文、蓝白科技风，按角色划分菜单；答辩演示路径可在 3 分钟内走完「浏览—纠错—审核—版本更新—通知」主线 |

## 3. 用户角色与权限

平台设置五类角色。角色采用 `sys_role` + `sys_user_role` 多对多建模，一个用户可同时具有多个角色（例如评审员同时也是普通用户），不把角色硬编码成布尔字段。

| 角色 | 主要职责 | 允许 | 禁止 / 受限 |
| --- | --- | --- | --- |
| 游客 | 浏览公开内容 | 查看已发布文章、公开作品、专题、活动；搜索 | 不能点赞、评论、收藏、投稿、提交贡献 |
| 普通用户 | 参与知识共建与互动 | 维护资料；提交知识贡献；评论、点赞、收藏、反馈；查看自己的贡献与通知 | 不能直接修改正式文章；不能审核任何投稿 |
| 创作者 | 创作并管理作品 | 含普通用户全部能力；发布/编辑本人作品；关联文章；参加活动投稿 | 不能修改他人作品；不能自行审核作品 |
| 评审员 | 处理审核任务 | 查看待审贡献与作品；通过/驳回并填写意见；对活动投稿评分 | 不能管理角色；不能无记录地修改正式文章 |
| 管理员 | 管理内容与活动 | 管理分类、文章、专题、作品、活动、评论与反馈 | 不涉及超级管理员专属的账号与系统配置 |
| 超级管理员 | 系统级管理 | 账号管理、角色分配、管理员/评审员账号管理、系统配置 | 危险操作需二次确认 |

**权限实现原则**（档案第 3、10 章）：所有受保护接口在后端校验角色与资源归属；前端菜单按角色动态渲染只是体验优化，不构成安全控制；操作者身份一律从认证上下文获取，不接受前端传入的 `reviewerId`、`roleCode` 等字段作为授权依据。

## 4. 功能需求

### 4.1 模块划分

| 编号 | 模块 | 核心价值 |
| --- | --- | --- |
| M1 | 科普知识库与专题探索 | 提供可信、可检索、可按主题组织的内容消费入口 |
| M2 | 创作者中心与作品管理 | 让知识以图文、漫画等形式二次表达，并与原文建立关联 |
| M3 | 知识共建与纠错 | 平台的差异化核心：带审核、带来源、带版本的内容演进 |
| M4 | 社区互动 | 评论、点赞、收藏、内容反馈，形成讨论氛围与质量监督 |
| M5 | 主题创作活动 | 用活动组织创作，包含发布、投稿、评审、优秀作品展示的闭环 |
| M6 | 消息通知与个人中心 | 把审核结果、回复、活动通知送达用户，并提供个人数据聚合 |
| M7 | 后台管理与系统管理 | 内容治理、审核工作台、账号与角色管理 |

### 4.2 关键需求与验收要点

**M3 知识共建（项目核心）**

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| FR-KC-01 | 对正式文章提交补充、纠错或修改建议 | 类型至少覆盖三种；建议内容、理由、参考来源均为必填 |
| FR-KC-02 | 提交者查看本人贡献记录 | 展示提交时间、审核状态、审核意见、处理时间 |
| FR-KC-03 | 评审员查看待审贡献并处理 | 审核必须填写意见；禁止无记录地直接覆盖建议原文 |
| FR-KC-04 | 审核通过后更新正式文章并保存历史版本 | 审核通过、版本快照、文章更新、贡献状态、通知写入在同一事务内完成；任一步失败整体回滚 |
| FR-KC-05 | 查看文章历史版本 | 记录版本号、旧内容快照、变更说明、操作者与时间；可追溯到来源贡献 |

**M2 作品与知识关联**

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| FR-WK-01 | 创作者创建、编辑、删除本人作品 | 仅限本人；已参加活动的作品删除需限制或提示 |
| FR-WK-02 | 作品关联一篇或多篇文章 | 关联目标必须存在且可访问；重复关联受唯一索引约束 |
| FR-WK-03 | 公开页面只展示已审核通过的作品 | 待审核、已驳回作品不得出现在公开列表 |

**M5 主题活动**

| 编号 | 需求 | 验收要点 |
| --- | --- | --- |
| FR-EV-01 | 管理员创建、发布、结束活动 | 字段含标题、说明、起止时间、参与规则、状态 |
| FR-EV-02 | 创作者在有效期内投稿 | 活动未开始或已结束一律拒绝；同一作品在同一活动只能投稿一次 |
| FR-EV-03 | 评审员对投稿评分并写评语 | 评分统一 1–5 分；同一评审员对同一投稿只保留一份有效评审，修改留痕 |
| FR-EV-04 | 展示优秀作品 | 由管理员确认获奖名单；未评审作品不得自动标为优秀 |

**M1 / M4 / M6 / M7** 的逐条需求见开发档案 4.1–4.7 节，本文不重复罗列，实现时以档案为准。

### 4.3 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 列表接口全部分页，单页上限 100 条；演示规模（千级数据）下页面响应在 1s 内 |
| 安全 | 密码 BCrypt 哈希存储；后端逐接口鉴权；SQL 全部参数化；用户提交内容展示时转义；敏感配置不入库不入 Git |
| 一致性 | 审核通过、版本快照、文章更新、通知写入在同一事务内；审核时检查状态仍为 PENDING，防止重复审批产生重复版本 |
| 可用性 | 列表具备加载中、空数据、请求失败、分页与筛选状态；错误提示面向用户，不暴露堆栈 |
| 可维护性 | 分层清晰（Controller/Service/Mapper/Entity/DTO-VO）；状态值后端统一定义，前端只负责展示 |
| 可追溯性 | 用户可见业务主体采用逻辑删除；审核、删除、发布等关键操作记入操作日志 |

## 5. 典型用例

**UC-01 知识纠错主线（答辩演示路径）**

1. 游客浏览文章详情，读到认为不准确的一段
2. 登录后点击「纠错」，填写建议内容、理由、参考来源，提交
3. 贡献状态为 PENDING，通知评审员
4. 评审员在审核工作台对照原文与建议，填写意见并通过
5. 后端在同一事务内：读取当前文章 → 写历史版本快照 → 更新正文与版本号 → 贡献置为 APPROVED → 写审核记录 → 生成站内通知
6. 提交者在个人中心与站内消息中看到结果；文章详情可查看版本历史，历史版本可追溯到该条贡献

**UC-02 作品创作与活动闭环**

1. 创作者创建作品，关联 1–2 篇科普文章，提交审核
2. 评审员审核通过，作品公开
3. 创作者在活动进行期间报名投稿
4. 活动结束后评审员评分，管理员确认优秀作品名单
5. 活动详情页展示优秀作品与评审摘要，相关用户收到站内通知

**UC-03 越权访问被拒绝**

普通用户直接调用管理员创建文章接口 → 后端返回 403 与统一错误结构；前端不依赖按钮隐藏来实现安全。

## 6. 范围边界

**明确不做**：商品交易、支付、购物车；纯文化展示型内容站；微服务、分布式架构、算法推荐、AI 自动审核作为必需项；全文检索引擎。

**优先级**：
- P0（必须完成）：七个模块主流程、角色权限、知识贡献审核与版本、事务一致性、基本测试
- P1（建议完成）：搜索分页细节、审核意见、贡献记录、优秀作品展示、反馈处理、操作日志、版本详情与恢复
- P2（可选增强）：图片上传、富文本编辑器、邮件通知、可视化统计、第三方登录、全文检索

**约束**：P0 未完成前不做 P2；任何偏离档案七模块核心特色的功能扩展需先说明理由。
