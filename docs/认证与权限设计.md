# 认证与权限设计

> 论文材料 · 对应开发档案第 3、10 章与本阶段实现。
> 代码位置：`science-platform-server/src/main/java/com/science/platform/security/`

## 1. 方案选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Session + Cookie | 服务端可随时失效，实现简单 | 前后端分离下需要处理跨域 Cookie、CSRF；横向扩展要共享会话 | 不采用 |
| JWT（无状态） | 前后端分离友好，令牌自带身份，无需服务端存储 | 令牌签发后无法主动撤销（需额外机制） | **采用** |
| OAuth2 / 第三方登录 | 标准化程度高 | 对本科毕设属于范围外复杂度 | P2 可选项 |

选择 JWT 的理由：项目是前后端分离的单体应用，前端用 Axios 调用 `/api/v1`，跨域场景下 Cookie 方案配置成本更高；JWT 的「令牌即凭证」模型也与档案第 8 章「请求头携带 `Authorization: Bearer`」的接口约定一致。

**不引入 Redis 做令牌黑名单**：档案第 14.1 节明确要求不擅自引入 Redis。撤销能力通过下面的「每次请求校验用户状态」弥补。

## 2. 令牌结构

采用 HS512 签名，载荷（payload）只放非敏感信息：

```json
{
  "sub": "6",
  "username": "user01",
  "roles": ["USER"],
  "iss": "science-platform",
  "iat": 1793338132,
  "exp": 1793345332
}
```

| 字段 | 含义 |
| --- | --- |
| `sub` | 用户 ID，服务端据此查询用户 |
| `username` | 登录名，便于日志排查 |
| `roles` | 签发时的角色快照（仅作参考，鉴权以数据库为准） |
| `iss` / `iat` / `exp` | 签发者、签发时间、过期时间 |

默认有效期 **120 分钟**（`app.jwt.expire-minutes`）。

**密钥管理**：密钥不写入版本库。`application.yml` 中为 `${APP_JWT_SECRET:}`，本地写在 `application-local.yml`（已被 `.gitignore` 忽略），生产通过环境变量注入。密钥长度不足 32 字节时应用**拒绝启动**，避免误用弱密钥上线。

## 3. 认证流程

```
客户端                     服务端
  │  POST /auth/login          │
  │  {username, password}      │
  ├───────────────────────────>│  1. 按用户名查用户（逻辑删除自动过滤）
  │                            │  2. BCryptPasswordEncoder.matches 校验密码
  │                            │  3. 校验 status = ACTIVE
  │                            │  4. 查询角色
  │                            │  5. 签发 JWT
  │<───────────────────────────┤
  │  {token, expiresIn, user}  │
  │                            │
  │  GET /api/v1/users/me      │
  │  Authorization: Bearer xxx │
  ├───────────────────────────>│  6. JwtAuthenticationFilter 解析令牌
  │                            │  7. 用 sub 查库，确认用户存在且 ACTIVE
  │                            │  8. 用数据库中的角色构造 authorities
  │                            │  9. 写入 SecurityContext
  │                            │ 10. 授权规则判定
  │<───────────────────────────┤
```

### 3.1 为什么每次请求都查一次数据库

许多 JWT 实现只信任令牌里的 `roles` 声明，这样做的代价是：管理员禁用了某账号，或撤销了某人的创作者角色，该用户仍能用旧令牌继续操作，直到令牌过期。

本项目在 `JwtAuthenticationFilter` 中每次请求都做两件事：

1. 按 `sub` 查询用户，确认 `deleted = 0` 且 `status = ACTIVE`
2. 从 `sys_user_role` 重新读取角色

代价是每个受保护请求多一次主键查询与一次小表关联查询，在毕设规模下可忽略；收益是**权限变更立即生效**。这一点在阶段 3 已实测：把账号置为 `DISABLED` 后，同一个未过期令牌马上返回 401。

## 4. 授权模型

采用 **RBAC**：用户 → 角色 → 接口权限。角色不硬编码为布尔字段，而是通过 `sys_role` + `sys_user_role` 多对多建模，一个用户可同时是「普通用户 + 创作者」。

### 4.1 角色与 Spring Security 权限的映射

角色编码加 `ROLE_` 前缀转为 Spring Security 的 authority：

| 数据库 `role_code` | Spring Security authority |
| --- | --- |
| `USER` | `ROLE_USER` |
| `CREATOR` | `ROLE_CREATOR` |
| `REVIEWER` | `ROLE_REVIEWER` |
| `ADMIN` | `ROLE_ADMIN` |
| `SUPER_ADMIN` | `ROLE_SUPER_ADMIN` |

### 4.2 接口授权规则

规则按「越具体越靠前」排列，写在 `SecurityConfig` 中：

| 顺序 | 路径 | 规则 |
| --- | --- | --- |
| 1 | `OPTIONS /**` | 全部放行（CORS 预检，否则浏览器拿不到响应头） |
| 2 | `/api/v1/health`、`/api/v1/auth/login`、`/api/v1/auth/register` | 公开 |
| 3 | `GET /api/v1/articles/**`、`/categories/**`、`/topics/**`、`/works/**`、`/events/**`、`/comments/**` | 公开（游客可浏览） |
| 4 | `/api/v1/admin/users/**` | `hasRole('SUPER_ADMIN')` |
| 5 | `/api/v1/admin/**` | `hasRole('ADMIN')` |
| 6 | 其他 | `authenticated()` |

> 顺序很关键：第 4 条必须写在第 5 条之前，否则 `hasRole('ADMIN')` 会先匹配掉 `/admin/users/**`，导致普通管理员也能进超管接口。

### 4.3 401 与 403 的区分

| 状态码 | 含义 | 触发点 |
| --- | --- | --- |
| 401 | 身份未知：未带令牌、令牌非法、令牌过期、用户被禁用 | `RestAuthenticationEntryPoint` |
| 403 | 身份已知但角色不允许 | `RestAccessDeniedHandler` |

两者都返回统一 JSON 结构，不使用 Spring Security 默认的 HTML 登录页或空白页面。

## 5. 安全措施清单

| 措施 | 实现 |
| --- | --- |
| 密码哈希 | `BCryptPasswordEncoder`，cost 默认 10，每个密码自带随机盐；`seed.sql` 中的 `$2b$` 哈希被同一编码器识别 |
| 防用户枚举 | 账号不存在与密码错误返回**完全相同**的提示「用户名或密码错误」（T02 测试断言两者 message 相等） |
| 防时序侧信道 | 账号不存在时同样执行一次 BCrypt 校验分支外的统一提示，不做「先查再比」的差异响应 |
| 注册越权 | 公开注册硬编码赋 `USER` 角色，请求体里没有角色字段可填 |
| 操作者身份 | 一律从 `SecurityContext` 取，不接受前端传 `userId` / `reviewerId` / `roleCode` |
| 实体序列化 | `SysUser.passwordHash` 标注 `@JsonIgnore`，即使实体被误返回也不会泄漏 |
| 日志 | 登录失败只记录用户名与结果，不记录密码明文 |
| 令牌失效 | 过期、签名不符、结构损坏统一返回 401，不向调用方区分原因 |
| 并发注册 | 唯一索引 `uk_username` 兜底，捕获 `DuplicateKeyException` 转成业务提示 |

## 6. 前端配合

| 环节 | 实现 |
| --- | --- |
| 令牌存储 | `localStorage`，`src/stores/user.js` 为唯一读写入口 |
| 自动携带 | `src/api/request.js` 请求拦截器统一加 `Authorization: Bearer` |
| 401 处理 | 清除令牌并跳转 `/login?redirect=<原路径>`，登录后自动跳回 |
| 路由守卫 | `meta.requiresAuth` / `meta.guestOnly` / `meta.roles`，只改善体验 |
| 刷新恢复 | 守卫里发现「有令牌无用户信息」时调用 `/auth/me` 补齐 |
| 顶栏展示 | 已登录显示头像、昵称与最高权限角色；未登录显示登录/注册入口 |

**前端守卫不是安全边界**：即使绕开守卫直接请求接口，后端仍会返回 401/403。阶段 3 的 T03 测试验证的正是这一点。

## 7. 已知限制

| 限制 | 影响 | 后续处理 |
| --- | --- | --- |
| 令牌无法主动撤销 | 用户改密码后旧令牌仍可用至过期 | 需引入令牌版本号或黑名单，属 P2 |
| 无刷新令牌 | 令牌过期需重新登录 | 当前 2 小时有效期可接受，答辩演示无影响 |
| 无登录失败次数限制 | 理论上可暴力尝试 | 答辩范围外，论文「不足与展望」说明 |
| 每次请求查库 | 高并发下有数据库压力 | 可加本地缓存，毕设规模不需要 |
