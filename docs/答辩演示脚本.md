## 第 3 幕：知识共建 —— 本项目最核心的流程（约 2 分钟）

这是**答辩的重点**，要讲清楚事务边界。

### 3.1 提交纠错（窗口 A，user01）

**页面**：`/knowledge/4`（光合作用那篇）

1. 点「提交纠错 / 补充」
2. 类型选「补充知识」
3. 建议内容填：`建议补充：卡尔文循环固定的二氧化碳先形成三碳糖，再分别合成蔗糖（运往其他器官）与淀粉（储存在叶绿体中）。`
4. 理由：`原文只写到生成糖类，读者不清楚产物去向。`
5. 参考来源：`植物生理学教材·光合作用章节`
6. 提交

**讲**：四个字段全必填，尤其是**参考来源**——这是它区别于普通评论的关键。

### 3.2 审核对照（窗口 B，reviewer01）

**页面**：`/review/contributions`

1. 点最新那条「处理」
2. **重点展示左右对照**：左边文章当前正文，右边用户建议
3. 往下拉到「最终采用的正文」——默认是原文，评审员可以把建议合并进去
4. 审核意见填：`建议准确，已合并进正文`
5. 点「通过并更新文章」

### 3.3 结果验证

**回到窗口 A**：

1. 导航「消息」→ 看到「知识贡献已通过」，点击可跳转
2. 回到 `/knowledge/4`，点「版本历史」→ 看到 **v1** 快照，变更说明写着
   「根据知识贡献 #68 采纳读者补充」

**这时要讲的话（核心）**：

> 一次「通过」在同一事务里完成了六件事：
> 读文章 → 写历史版本快照 → 更新正文与版本号 → 改贡献状态 → 写操作日志 → 发站内通知。
> 任一步失败整体回滚，不会出现「文章改了但没历史版本」的中间状态。
>
> 状态更新用的是 `WHERE id = ? AND status = 'PENDING'` 条件更新，
> 两个评审员同时点通过时，第二个人的 affected 是 0，会触发回滚——不会产生两条快照。

**如果有老师追问**：可以直接说做过事务回滚测试（T09），用 mock 让写快照抛异常，
验证文章版本号、正文、贡献状态、通知、日志全部保持原样。

## 第 5 幕：主题活动闭环（约 1 分钟）

**页面**：`/events`

1. 活动 1「星际漫游者」显示**进行中**，活动 2「地球回响」显示**已结束**
2. 点活动 2 → 看「优秀作品」区块（一等奖：碳足迹的一天）

**讲时间状态的设计**：

> 「进行中 / 已结束」不是存的字段，是每次读取时按当前时间算的。
> 如果存成字段就得靠定时任务翻状态，任务没跑就会出现「时间过了但还能投稿」的窗口期。

3. 点活动 1 → 「提交作品参赛」（用 creator01 登录）→ 选择作品提交

**切到 reviewer01** → `/review/events` → 给投稿打分（1–5 分 + 评语必填）

**切到 admin01** → `/admin/events` → 点「确认优秀作品」

**这里有个可以展示细节**：未评审的投稿，获奖下拉框是**禁用**的。

> 「档案要求不能把未评审作品自动标为优秀，所以后端会逐条校验有没有评审记录，
> 一条没有就整体拒绝；前端也把下拉框禁用了。」

## 第 6 幕：权限边界（约 30 秒）

**窗口 A（user01）**：手动在地址栏输入 `http://localhost:5173/admin`

→ 被前端守卫拦下并提示无权限

**再讲后端**：

> 前端拦截只是体验优化。真正的边界在后端——普通用户直接调 `/admin/**` 一律 403。
> 验收里专门测了：普通用户调管理接口 403、管理员调超管接口也 403。

可以用浏览器开发者工具或 Postman 演示一次 403 返回的统一 JSON 结构。

## 第 7 幕：后台管理（约 40 秒）

**用 admin01 登录** → `/admin`

快速过一遍左侧菜单：

- 文章管理：草稿/已发布/已下架状态流转
- 分类管理：文章与作品分类共用一张表，靠 type 区分
- 专题管理：可以编排专题内的文章顺序
- 活动管理：发布、结束、确认获奖
- 内容反馈：处理用户反馈

**用 superadmin 登录** → 「用户与角色」

**这里讲两个防锁死规则**：

> 不能移除自己的超管角色，也不能禁用当前登录的账号——否则一次误操作就把自己关在系统外面。

**可以现场演示**：给 user01 加「创作者」角色，然后**用原来那个令牌**去访问创作者中心，从 403 变 200。

> 「因为鉴权过滤器每次请求都重新查库取角色，所以权限变更立即生效，不需要重新登录。」

## 常见追问与回答

| 问题 | 回答要点 |
| --- | --- |
| 为什么用 JWT 而不是 Session？ | 前后端分离，跨域下 Cookie 方案配置成本更高；JWT 与档案 8.3 的接口约定一致 |
| JWT 不能主动撤销怎么办？ | 过滤器每次请求查库校验用户状态与角色，禁用账号立即生效；令牌黑名单属于 P2 |
| 为什么用 LIKE 不用全文检索？ | 档案要求「不引入复杂搜索引擎」，演示规模下 LIKE 足够；已在「不足与展望」说明 |
| 版本号为什么是「变更前」的内容？ | 审核流程是先快照再更新，所以存的是被覆盖的旧内容；`version_no = N` 表示当前第 N 版 |
| 评论为什么只做一层回复？ | 控制渲染与排序复杂度，档案未要求多层 |
| 测试是真实跑的吗？ | 109 个用例全部真实连库执行，部分用 `@MockitoBean` 模拟失败场景验证回滚 |
| 如果两个人同时点赞会怎样？ | 唯一索引兜底，插入冲突捕获后视为已点赞；实测连点 3 次只留 1 条 |
